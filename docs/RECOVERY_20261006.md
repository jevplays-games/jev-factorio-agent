# October 6 recovery: distinguish policy, planner and monitoring failures

Use the supervisor result and console exception before deciding that another
stop is the same incident. The campaign had three distinct failure modes:

| Evidence | Cause | Recovery |
| --- | --- | --- |
| Live controller; low JEV choice confidence; no exception | Strict policy hold | Preserve the threshold and attempts. Use the reviewed two-stage protocol; do not force an action or reroll unchanged inputs. |
| Exit 1 at 07:34 UTC; `Native production cycle` through gears and a burner inserter | Buffer construction reused the suspended science recipe's dependency path | Reproduce with the accepted observation and capital failure history. Plan the bounded buffer component with a separate recipe path while prohibiting nested buffer acquisition. |
| At 09:06 UTC libvirt reports no complete agent response in 10,485,760 bytes; monitor reports probe unavailable | An oversized diagnostic response exceeded the agent transport limit | Restore only the affected guest-agent connection; preserve the guest and campaign. Retrieve bounded summaries or chunks thereafter. |

The planner crash occurred after the campaign exhausted its capital investment
attempts and recompiled ordinary production. Its partly built iron output buffer
needed an inserter. That inserter needed a gear, but the outer science demand
already contained a gear dependency. This was a false cycle between two demands.
The fix retains real cycle detection within the component recipe and preserves
the original capital failure counts. The captured regression proposes one gear
craft costing two of the actor's three iron plates; it is offline evidence,
not a claim that this action was executed in production.

## Efficient incident procedure

1. Read the existing owner, child process, terminal result, checkpoint identity
   and pending work. Keep a bounded console tail and accepted observation. Do
   not restart an intentionally held supervisor or start a second controller.
2. If the probe fails, separately check host uptime, VM state, block errors,
   lease identity and guest-agent connection. Running QEMU is not proof that
   the controller runs. Refused SSH is not proof of a guest crash: this guest
   had no SSH service installed.
3. For this transport incident, the guest agent was alive and direct socket
   synchronization/ping worked after draining retained output. Restarting only
   the guest-agent service did not restore libvirt's connection. Detaching and
   reattaching the exact affected live channel restored normal probes. Save its
   original XML and record each one-use operation; do not restart shared
   libvirt, WSL, Train, Factorio or other guests for this diagnosis.
4. Bound guest-agent responses well below the transport limit, accounting for
   base64 and envelope expansion. Do not return a complete multi-megabyte event
   log in one response. Prefer guest-side filtering, hashes and bounded chunks.
5. Reproduce the exact planner frontier with retained failures and reservations.
   A replay without failure history can select another capital investment and
   conceal this crash. Run regression and compatibility tests before signing
   and publishing the repair.
6. If a proven planner exit left the checkpoint marked running, use
   `planner_fault_recovery.prepare` with the exact checkpoint, terminal, console
   and sealed research pins after stopping the existing owner and child. It
   requires the already-held writer lock and refuses any native or provider
   activity in the final failed decision. Review its proposal: only status,
   reason and a separate fault-proof field may change; history, failures and
   prior attempts must remain identical. Retain the original capture and
   install the reviewed proposal once under the owner lock. This records the
   actual planner fault, not a low-confidence decision.
   When the normal changed-source admission is consumed, the first prepared
   two-stage decision and its running workflow status are saved together. The
   original fault proof stays in the checkpoint. Running here permits phase
   recovery; only a verified native action establishes useful game progress.
7. Deploy through the campaign's existing source/owner admission, single-writer
   lock and native/CLI preflight. Preserve receipts, attempts, history, source
   lineage and save identity. A new source revision alone is not retry authority.
8. Verify fresh useful native actions and the actual OBS Program output. The
   repaired monitor must distinguish stopped, policy-blocked and progressing
   states. Start the 24-hour acceptance window only after recovery; any manual
   recovery starts that qualification window again.

Restoring monitoring established that the guest and Factorio survived while the
controller had exited. The monitor and OBS Program then correctly showed
`JEV stopped: controller process unavailable`. No guest/host reboot was needed.
Multi-day gameplay remains a separate production acceptance requirement.
