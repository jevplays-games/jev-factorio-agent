# Windows checkpoint installation guarantees

Checkpoint writes use a same-directory temporary file, flush and `os.fsync` its contents, then install it with `os.replace`. On Windows the temporary handle is closed before replacement and the installed file is reopened. The save is accepted only after the installed entry still matches the flushed file's stable identity and exposed metadata, the path and open-handle stamps are each unchanged across final verification, and a bounded read matches the exact serialized bytes. A failed save clears the in-memory coalescing cache; the controller's persistence barrier continues to refuse later mutations after a checkpoint failure.

Windows Python can report different `st_ctime_ns` values for `Path.stat()` and `os.fstat()` on the same installed file, and the flushed temporary handle can report a different `st_birthtime_ns` from the path and reopened handle. In the reproduced Windows 11 / Python 3.14.3 case, device, file index, size, modification time, mode, file attributes, and link count agreed across these views. The comparison therefore keeps both time fields in each full path/descriptor stamp and compares those stamps within their own metadata view across final verification. On Windows, cross-view and pre/post-rename comparisons use the common file identity and exposed metadata fields, excluding ctime and birth time; file bytes remain independently verified. POSIX path/handle identity remains exact, and the pre-rename comparison continues to allow only the rename-related ctime change. File mode, Windows file attributes, size, mtime, device, file index, and link count stay part of the cross-view identity checks.

This is a race-detection boundary for the single operational owner, not an interprocess lock or an ABA proof. Replacements and exposed metadata changes are rejected, and same-size content edits remain rejected even when timestamps collide.

The code still calls `os.fsync` for the checkpoint file on Windows. Python does not provide a portable Windows parent-directory `fsync` guarantee here; Windows reports zero directory-sync calls, and this implementation does not claim that an atomic rename is durable across sudden power loss. On POSIX, file `fsync`, containing-directory synchronization, synchronization of newly created parent entries, and parent identity checks remain in force.
